# ギャップの調べ方

要件と既存のコードの差を調べ、設計の段階で実現のしかたを決める材料にします。深い調査は設計の段階に回し、
ここでは差と選択肢を短くまとめます。

## 1. 今の状態

- 要件に関係するパッケージ、ファイル、型、関数
- 使い回せる部品（`@ugoke/core` の型と Port、`@ugoke/definition` の検証、既存の Adapter など）
- 守るべき約束事（`CLAUDE.md` のアーキテクチャと規約、パッケージの依存の向き、テストの置き方）
- 触れる境目（定義の形式、JSON Schema、設定、Workflow の履歴、CLI の出力）

## 2. 要件を満たすのに要るもの

要件の受け入れ基準ごとに、次のどれに当たるかを書きます。

- **ある:** 既存のコードで満たせる
- **足りない:** 新しく作る必要がある
- **変える:** 既存のコードを変える必要がある。互換性への影響があれば書く
- **要調査:** 今の時点ではわからない。設計の段階で調べることとして短く書く

## 3. 実現のしかたの選択肢

当てはまるものを挙げ、それぞれの利点と欠点を短く書きます。

- **既存を広げる:** 既存のファイルや部品に足す。ファイルが少なく済むが、既存のものが膨らむ
- **新しく作る:** 責務が違うなら、新しいファイルやパッケージにする。分かれて見通しがよいが、境目の設計が要る
- **組み合わせる:** 一部を広げ、一部を新しく作る

Adapter を足すときは、`adapter-<種類>-<実装>` の個別のパッケージにする約束事があります。

## 4. 複雑さとリスク

- **大きさ:** 小（数ファイル）、中（1 つのパッケージの中で複数の部品）、大（複数のパッケージにまたがる）
- **リスク:** 高、中、低と、その理由（Workflow のリプレイへの影響、公開している形式の変更、外部への依存など）

## 報告の形

ギャップは、次の形で短くまとめます。

```markdown
### 今の状態

- ...

### 受け入れ基準ごとの差

| 基準 | 差       | メモ                                           |
| ---- | -------- | ---------------------------------------------- |
| 1.1  | ある     | `packages/definition/src/...` の検証で満たせる |
| 1.2  | 足りない | ...                                            |

### 実現のしかたの選択肢

- ...

### 複雑さとリスク

- 大きさ: 中
- リスク: 中（...）

### 要調査

- ...
```
