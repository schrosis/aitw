# sdd-design

承認された要件をもとに、設計の文書を書きます。設計は、タスクを分けるときと、並べて進められるかを
決めるときの根拠になります。特に「境界」と「ファイルの構成」は、タスクの段階がそのまま使います。

## 手順

1. [約束事](../../sdd/conventions.md) と [置き場](../../sdd/storage.md) を読む
2. 置き場から要件の文書を読む。なければ止めて、`sdd-requirements` を案内する
3. 依頼にギャップの調査の結果（`sdd-validate-gap` の報告）があれば読む。なければ、同じ観点で既存のコードを
   軽く調べる
4. 設計に関わる既存のコードを調べる。使う型、関数、ファイルが、本当にその形で存在するかを確かめる
5. [雛形](templates/design.md) に沿って、下書きを作る
6. [書く前の関門](rules/review-gate.md) で下書きを確かめ、直せるものは直す。関門の確かめと直しは
   2 回までにする。要件が曖昧で設計を決められないときは、推測で埋めず「未決の論点」に書く
7. 置き場の設計の文書に書く
8. 約束事の「報告」の形で報告する

## ugoke で特に確かめること

- パッケージの依存の向き（`CLAUDE.md` のアーキテクチャ）。`@ugoke/engine` は `@ugoke/core` だけに依存する
- Workflow のコードは `packages/engine/src/workflows` に置き、Node API と副作用を持ち込まない。副作用は
  Activity で実行する
- Workflow のコードを変えるなら、記録した履歴をリプレイできるか。できないなら `workflowCodeVersion` を
  上げて履歴を記録し直すことを、互換性と実装計画に書く
- 定義の形式を変えるなら、JSON Schema の再生成と、`ugoke validate` の検証を設計に含める
- 関数はアロー関数で書く
- 要らない抽象を作らない。今の要件にない将来のための部品は設計しない
