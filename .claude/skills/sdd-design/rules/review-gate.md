# 設計を書く前の関門

設計の文書を書く前に、下書きを次の順で確かめます。直せるものは下書きを直して、もう一度確かめます。

## 機械的な確かめ

- **要件の対応:** 要件の文書からすべての受け入れ基準の番号を拾い、「要件の対応」の表にすべてあることを
  確かめる。抜けている番号を書き出して直す
- **境界が埋まっている:** 「境界」の「持つもの」「持たないもの」「依存してよいもの」が、空や仮の文字だけでない
- **ファイルの構成が埋まっている:** 「ファイルの構成」の表に、具体的なパスがある。「未定」だけの行がない
- **部品とファイルの対応:** 設計に出てくる部品（型、関数、モジュール）が、ファイルの構成のどれかのパスにある
- **境界とファイルの一致:** ファイルの構成が、境界で「持つもの」より広い責務を示していない

## 要件の網羅

- すべての受け入れ基準が、具体的な部品、データの流れ、エラーの扱い、テストのどれかで裏付けられている
- 外部への依存、互換性、エラー、性能に関わる要件が、設計に明示されている
- 要件にない機能を設計していない

## 実装できるか

- 部品の境界がはっきりしていて、タスクに分けるときに持ち主を推測しなくてよい
- 型、関数の形、データの流れ、エラーの扱いが、実装とテストに十分なほど具体的
- 前提として要るもの（パッケージの追加、Schema の再生成、履歴の記録し直しなど）が書かれている
- 実装計画の順で進めて、途中でも `pnpm check` が通る

## 並べて進められるか

- 互いに依存せず、変えるファイルが重ならない部品の組が、実装計画で見えている
- 同じファイルを多くの部品が触る設計になっていない。なっているなら、共有する部分を先に作る順にする
