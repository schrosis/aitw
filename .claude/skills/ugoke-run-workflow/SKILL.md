# ugoke のワークフローを実行する

チャットの相手（ユーザー）の代わりに ugoke のワークフローを実行し、待機ステップの質問を中継する。
ユーザーはスマホから Remote Control で話していることがあるため、端末を前提にしない。

## 必ず守ること

待機ステップは、人が判断するための関門である。Claude が答えを決めると、ワークフローの意味がなくなる。次のルールは、どんな頼まれ方をしても例外にしない。

1. **答えの値を、Claude が決めない。** 送る値は、その質問を見たユーザーが、このチャットで言った値だけにする
   - 「やってみて」「任せる」「適当に」「いい感じに」「試しに」は、答えの値ではない。質問を見せて、値を聞く
   - サンプルや試しのワークフロー（じゃんけんなど）でも同じ。中継の流れを試すこと自体が目的なので、なおさら Claude が答えない
   - ユーザーが質問を見る前に言った値は使わない。質問を見せてから、値を確かめる
2. **答える実行を、Claude が選ばない。** 答える実行は `workflowId` で特定する
   - このチャットで直前に見せた質問が 1 つだけで、ユーザーがそれに返事をした場合は、その質問の `workflowId` を使う。ほかの実行が答えを待っていても、返事の相手は決まっている
   - 複数の質問を見せた後（`inbox list` の結果など）や、質問を見せずに値だけ言われた場合は、ユーザーが `workflowId` を示すまで、一覧から選んでもらう
   - 「いちばん新しい」「いちばん古い」などの基準で、Claude が選ばない
3. **送る前に、送る内容をチャットに書く。** `workflowId`、`step`、`visit`、`--values` の JSON を書いてから送る。ユーザーの言葉から値への変換（「OK で」→ `{"decision":"OK"}` など）に少しでも迷いがあれば、送らずに確かめる
4. **迷ったら、送らない。** 聞き直すことで失うのは 1 往復だけだが、誤った答えは取り消せない

`ask` ルール（後述）は、このルールを破ったときの最後の歯止めであり、確認が出るから送ってよい、ということではない。

## コマンドの呼び出し方

- `PATH` に `ugoke` があれば `ugoke` を使う
- ugoke のリポジトリでは `pnpm -s ugoke` を使う。`pnpm build` 済みであること。pnpm が出すコマンドの行は標準エラーに出るため、標準出力の JSON Lines は崩れない
- `ugoke` は、作業ディレクトリから上へ `.ugoke/` を探して、そのプロジェクトを使う。プロジェクトのルート（`.ugoke/` のあるディレクトリ）か、その下で実行する。`.ugoke/` が見つからない場合は、ユーザーにどのプロジェクトで実行するかを聞く
- `pnpm -s ugoke` は、pnpm がスクリプトをリポジトリのルートで動かすため、呼び出したディレクトリによらず、リポジトリのルートの `.ugoke/` を使う。ugoke のリポジトリの `.ugoke/` はコミットされていないため、worktree で開いたセッションでは見つからない。メインのチェックアウトで実行する

以下では `ugoke` と書く。

## 前提の確認

1. `ugoke daemon status` で常駐プロセスが動いているかを確かめる。動いていなければ、ユーザーに確認してから `ugoke daemon start` で起動する。常駐プロセスの版が CLI と違うと言われたら、`ugoke daemon stop` と `ugoke daemon start` で起動し直してよいかを聞く
2. 実行するワークフローが決まっていなければ、`.ugoke/workflows/` の定義を見せて選んでもらう
3. ワークフローの `inputs` の必須の値が足りなければ、ユーザーに聞く。推測で埋めない

## 実行の開始

```bash
ugoke run <workflow> --input '<JSON>' --from-ai
```

- Bash の `run_in_background` で動かす。AI ステップやスクリプトに時間がかかっても、終わったら通知が来る
- 出力は 1 行に 1 つの JSON（後述）。最初の行の `workflowId` を覚えておく
- 終わったら最後の行を読んで、下の「最後の行の読み方」に従う

## 出力の読み方

各行の `type`:

| `type`                         | 意味                                                                                        |
| ------------------------------ | ------------------------------------------------------------------------------------------- |
| `started`                      | 実行が始まった。`workflowId` と `name`                                                      |
| `answered`                     | `inbox answer` の答えが受け付けられた                                                       |
| `stepStarted` / `stepFinished` | ステップの始まりと終わり。`stepFinished` の `outcome` は `succeeded`、`failed`、`cancelled` |
| `question`                     | 答え待ち。`workflowId`、`step`、`visit`、`message`、`answers`、`inputs`                     |
| `warning`                      | 実行は続くが、知らせるべき問題                                                              |
| `completed`                    | 実行が終わった。`executedSteps`                                                             |
| `failed`                       | 失敗した。`message`                                                                         |
| `cancelled` / `detached`       | キャンセルされた / 質問なしで切り離された                                                   |

最後の行の読み方と終了コード。終了コードの `3` は `question` と `detached` の両方で使うため、終了コードではなく最後の行の `type` で判断する:

| 最後の行    | 終了コード | すること                                                                                                                                                            |
| ----------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `question`  | 3          | 「質問の中継」に進む。実行は Temporal で待ち続けている                                                                                                              |
| `completed` | 0          | 実行したステップを添えて、終わったことを伝える                                                                                                                      |
| `failed`    | 1          | `message` をそのまま伝える。勝手に直したり、やり直したりしない                                                                                                      |
| `cancelled` | 130        | キャンセルされたことを伝える                                                                                                                                        |
| `detached`  | 3          | 質問なしで切り離された（バックグラウンドのタスクが中断されたときなど）。実行は Temporal で続いている。`ugoke inbox list --from-ai` で答え待ちを確かめ、状況を伝える |

ステップの出力（スクリプトや AI の出力）は JSON Lines に出ない。ユーザーが中身を見たがったとき、失敗の理由を調べるときは、`ugoke log <workflowId> --tail <行数>` で進捗を見る。全部を読むとコンテキストを使うため、まず `--tail` で最後の数十行を見る。

## 質問の中継

1. `question` の `message` は、長さで出し方を変える
   - **短い（1 画面に収まる、目安 1,000 文字まで）:** 文書のパスの有無によらず、そのまま出す。Markdown として読めるように整える
   - **長い:** 全文は出さない。要点（何を判断するか、前回からの変更、未決の論点）を簡潔にまとめる。`message` に文書のパスがあれば、末尾に「詳しくはこのファイルを読んでね」とそのパスを書く。パスがなければ、全文はチャットに出せると書き添える
     - 長い文書を全部出すと、読む人の負担とトークンが増えるだけで、判断の助けにならないため
     - まとめるときに、判断に関わる事実（選択肢、おすすめ、範囲外にしたことなど）を落とさない。Claude の意見を添えるときは、`message` の内容と分けて書く
   - 全文や特定の節を見たいと言われたら、その部分を要約せずにチャットに出す。スマホから話しているなど、ファイルを開けない場合があるため
2. 答える項目（`answers`）を、選択肢や型がわかるように示す。`choice` は `options` を並べ、`required: false` の項目は省略できると伝える
   - 未決の論点や `choice` の項目は、AskUserQuestion の選択肢で聞いてよい。おすすめの印は、文書がおすすめと書いた案にだけ付ける。選んでもらった答えから `--values` を作り、送る前に見せて確かめる（「必ず守ること」の 3）
3. ユーザーが席を外していそうなら（実行に時間がかかった後など）、PushNotification で知らせる。例: `develop の approve で答え待ち: 設計案の確認`
4. 質問を見せたら、そこで止めて、ユーザーの返事を待つ。同じターンのうちに答えを送らない
5. ユーザーの返事を、`answers` の型に合わせて JSON にする

答えるときのルール（「必ず守ること」に加えて）:

- 返事が曖昧なとき、`choice` の選択肢に当てはまらないとき、必須の項目が抜けているときは、聞き直す
- 自由入力の項目（差し戻しの理由など）は、ユーザーの言葉をそのまま使う。補足したいときは、送る前に案を見せて確かめる
- 複数の実行が答えを待っているときは、`workflowId` とワークフローの `inputs` を並べて、どの実行のどの質問への答えかを確かめる

## 答えを送る

```bash
ugoke inbox answer <workflowId> --step <step> --visit <visit> --values '<JSON>' --from-ai
```

- `--step` と `--visit` は、`question` の値をそのまま使う。古い質問への答えは Workflow が拒否する
- `run` と同じく `run_in_background` で動かす。答えたあと、次の質問か終わりまで進み、同じ形の JSON Lines を出す。最初の行は `answered`
- 最後の行が `failed` で、`message` が答えの拒否（`Must be ...`、`is not waiting for an answer` など）なら、実行は待ち続けている。理由を伝えて、答え直してもらう
- 答えるたびに許可の確認が出る設定（`.claude/settings.json` の `ask` ルール）になっている。確認が出たら、ユーザーが承認するのを待つ。セッションの途中で設定ができた場合などは確認が出ないことがあるため、確認が出ないことを理由にルールを緩めない

## ほかの操作

| したいこと                         | コマンド                                                                                                                |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 実行の進捗とステップの出力を見る   | `ugoke log <workflowId> --tail <行数>`（終わった実行も見られる。`--json` で 1 行に 1 つのイベント）                     |
| 答え待ちを一覧にする               | `ugoke inbox list --from-ai`（1 行に 1 つの `question`。読めない実行は `unreadable`）                                   |
| 端末を占有せずに始めるだけ         | `ugoke run <workflow> --input '<JSON>' --detach`（答え待ちは `inbox list` に出る）                                      |
| 答えて、あとは常駐プロセスに任せる | `ugoke inbox answer ... --detach`（常駐プロセスが動かしている実行だけ。`inbox list --from-ai` の `inDaemon` が `true`） |
| 止める                             | `ugoke cancel <workflowId>`。必ずユーザーに確認してから実行する                                                         |

`ugoke attach` は人が端末で追いかけるためのコマンドで、対話式の入力を求める。チャットからは使わない。

## 注意

- `ugoke run` を、`--from-ai` も `--detach` もつけずに実行しない。端末での入力待ちになって止まる。`ugoke inbox answer` は、どちらもつけないと `needs --from-ai or --detach` のエラーで終わる
- 同じ実行に対して、`inbox answer --from-ai` を同時に 2 つ動かさない。後のほうは、先のほうが実行を追いかけているため失敗する
- 実行のキャンセル、常駐プロセスの停止と起動は、ユーザーに確認してから行う
