# タスクの分け方

## 構造

タスクは 3 つの層で書きます。

- **Wave:** 並べて進められる PR のまとまり。`## Wave 1` のような見出しにする
- **大タスク:** 1 つの PR。1 つのブランチで実装し、1 回のレビューを受ける
- **サブタスク:** PR の中の作業の単位。上から順に実装する

今の `develop` は、Wave の順に PR を 1 つずつ実装します。将来は、同じ Wave の PR を並べて実装します。
今から、並べても壊れない分け方にしてください。

## 番号

- 大タスクには 1、2、3 と、Wave をまたいで通し番号を振る
- サブタスクには、大タスクごとに 1.1、1.2、2.1 と振り直す
- 3 層目（1.1.1）は作らない
- 実装を始めた後に大タスクを足すときは、今ある番号を振り直さず、最大の番号の次を振る。番号が並び順と
  ずれてもかまわない。`develop` と実装メモが、番号で大タスクを指しているため
- サブタスクが 1 つだけになる大タスクは、サブタスクを作らず、詳細を大タスクに直接書く

## PR の大きさ

PR ごとのレビューは、AI と人間の手間がかかります。細かく分けすぎないでください。

- 1 回のレビューで見られる範囲で、関係するサブタスクを 1 つの PR にまとめる
- サブタスクのない、小さな PR は、ほかとまとめられない理由があるときだけにする。たとえば、ほかの PR の
  前提になる、または境界が違うため同じ Wave で並べたい
- どの PR を終えた時点でも、`pnpm check` が通るようにする
- PR は、設計の 1 つの境界の中に収める。複数の境界をつなぐ作業は、つなぐための PR にする

## サブタスク

- 1 つの、確かめられる成果を持つ。複数の、別々に確かめられる成果があれば分ける
- 何ができるようになるかを、設計の部品の名前を使って書く。型の定義や関数の形は設計に任せ、ここに書き写さない
- 詳細の 1 つには、終わったときに何が確かめられるか（振る舞い、テストの結果など）を書く
- 最後の詳細に `_Requirements: 1.1, 1.2_` の形で、満たす受け入れ基準の番号だけを書く。説明やかっこを添えない
- テストは、実装と同じサブタスクに含める。テストだけを後回しにしない

## Wave

- 同じ Wave の PR は、互いに依存しない
- 同じ Wave の PR は、`_Boundary:_` が重ならない。設計の「ファイルの構成」で、同じファイルを触らないことを確かめる
- PR が依存してよいのは、前の Wave の PR だけにする
- 共有する土台（型、共通の部品、設定、テストの仕組み）は、早い Wave に置く。中核の機能は並べやすいので、
  同じ Wave に並べる。つなぐ作業と全体の確かめは、後の Wave に置く
- PR が 2 つ以上ある Wave では、各 PR の番号の後に `(P)` を付ける

## PR の注釈

大タスクの行の直後に、2 つの空白で字下げして、次の注釈を書きます。

- `_Branch: <ブランチ名>_`（必ず書く）: 変更の種類（feat、fix、refactor、test、docs、chore など
  Conventional Commits の type）と、変更を表す短い英語の kebab-case を `/` でつなぐ（例:
  `feat/github-pr-plugin`）。PR ごとに違う名前にする
- `_Boundary: <部品の名前>、<部品の名前>_`（必ず書く）: 設計の「ファイルの構成」の部品の名前
- `_Depends: 1, 2_`（前の Wave の PR の成果を使うときに必ず書く）: 依存する大タスクの番号だけを書く。
  `develop` は、ここに書いた PR が終わっていなければ実装を始めない

## タスクにしないもの

`develop` の AI ができない作業は、タスクにせず、文書の最後の `## 人間が行う作業` の節に、`- ` で始まる
行で書きます。どの PR の後に行うかを添えてください。なければ、その節は書きません。

- `.ugoke/` の下の変更。`develop` は、実行中にワークフローの定義を変えないよう、`.ugoke/` を変えられない
- `README.md` と `docs/` の更新。ドキュメントは人間が体裁を整えてからコミットする
- デプロイ、リリース、手で行う確認

## 実装メモ

`## 実装メモ` の節は書かないでください。`develop` が、実装の中で得た、後の PR に役立つ知見を書き足します。
差し戻しで直すときに、この節がすでにあれば、そのまま残してください。

## 形の決まり

`develop` はスクリプトで読むため、次の形を守ってください。

- 大タスクの行は、行の先頭から `- [ ] <番号>. ` で始める。`(P)` は番号の後に置く: `- [ ] 2. (P) PR の名前`
- サブタスクの行は、行の先頭から `- [ ] <番号>.<番号> ` で始める: `- [ ] 2.1 サブタスクの名前`
- 行の先頭の `- [ ] ` は、大タスクとサブタスクの行のほかには書かない
- 大タスクとサブタスクの詳細は、2 つの空白で字下げした `- ` で書く
- PR の注釈は、大タスクの行と最初のサブタスクの行のあいだに書く
- `develop` は、大タスクの行から、次の大タスクの行か見出しの前までを 1 つの PR として読む

## 書く前の関門

タスクの文書を書く前に、下書きを次のことで確かめます。

### 網羅

- 要件の文書のすべての受け入れ基準の番号が、どれかのサブタスクの `_Requirements:_` にある
- 設計の「ファイルの構成」のすべての部品が、どれかの PR の `_Boundary:_` にある
- 前提として要るもの（パッケージの追加、Schema の再生成、履歴の記録し直しなど）が、それを使う PR より前にある

### 実装できるか

- 各サブタスクに、確かめられる成果と、終わったときに確かめられることがある
- PR を上から順に終えたとき、どの時点でも `pnpm check` が通る
- 暗黙の前提が残っていない

### Wave と PR

- 同じ Wave の PR が、互いに依存せず、境界が重ならない
- `_Depends:_` が前の Wave の PR だけを指し、前の PR の成果を使う PR にはすべて書かれている
- 細かすぎる PR や、1 回のレビューで見られないほど大きい PR がない
- ブランチ名が形に合い、PR ごとに違う
- 形の決まりを守っている
