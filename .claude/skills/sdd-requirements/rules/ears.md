# EARS の書き方

受け入れ基準は EARS（Easy Approach to Requirements Syntax）の形で書きます。条件、主語、振る舞いの組み立てで
書くことで、テストで確かめられる、曖昧さの少ない基準にします。

## 形

| 種類         | 形                                             | 使うとき                   |
| ------------ | ---------------------------------------------- | -------------------------- |
| 常に成り立つ | `<主語> は <振る舞い> する`                    | いつも成り立つ性質         |
| できごと     | `<契機> とき、<主語> は <振る舞い> する`       | 何かが起きたときの応答     |
| 状態         | `<状態> の間、<主語> は <振る舞い> する`       | ある状態のあいだの振る舞い |
| 望まない状況 | `もし <状況> なら、<主語> は <振る舞い> する`  | エラー、失敗、想定外の入力 |
| 任意の機能   | `<機能> がある場合、<主語> は <振る舞い> する` | 設定や定義で選べる機能     |

組み合わせてもかまいません。

- `<状態> の間に <契機> とき、<主語> は <振る舞い> する`
- `<契機> とき、<条件> なら、<主語> は <振る舞い> する`

## 例

- 1.1 `ugoke run` は、定義の検証に失敗したワークフローを起動しない
- 1.2 待機ステップに答えが届いたとき、Worker は答えを `result` に入れて次のステップに進む
- 1.3 もし `maxVisits` を超えてステップに入ろうとしたなら、Workflow は、そのステップを実行せずに失敗にする
- 1.4 `continueOnError` が `true` の場合、Workflow は、ステップが失敗しても `result.ok` を `false` にして続ける

## 主語

主語には、振る舞いを持つ具体的なものを書きます。

- ugoke 全体の振る舞いなら `ugoke`
- 利用者が触るものなら、そのコマンドや機能（`ugoke run`、`ugoke validate`、定義の検証、待機ステップなど）
- 実行の仕組みなら、その担い手（Workflow、Worker など）

## 良い基準

- テストか手で確かめられる
- 1 つの基準に、1 つの振る舞いを書く
- 「速く」「適切に」「安全に」のような曖昧な言葉を使わない。確かめられる形に言い換える
- 「する」は必ず満たすこと、「するのが望ましい」は推奨に使い分ける
