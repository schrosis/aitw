# sdd-validate-design

設計の文書を検証します。完璧さではなく、実装に進んでよいかを判断します。結果は報告するだけで、
文書もコードも変えません。

## 手順

1. [約束事](../../sdd/conventions.md) と [置き場](../../sdd/storage.md) を読む
2. 置き場から要件と設計の文書を読む。どちらかがなければ止めて、書くスキルを案内する
3. 先に [設計の関門](../sdd-design/rules/review-gate.md) の機械的な確かめを行う
4. 既存のコードを調べながら、下の観点で確かめる
5. 実装を大きく損なう問題だけを、重い順に 3 つまで選ぶ
6. 下の形で報告する

## 観点

- **既存の構成との整合:** `CLAUDE.md` のアーキテクチャ、パッケージの依存の向き、既存のモジュールの分け方に沿うか。
  Workflow のコードに Node API と副作用を持ち込んでいないか。副作用を Activity で実行するか
- **互換性:** 記録した履歴のリプレイ、定義の形式、JSON Schema、設定、CLI の出力への影響を見落としていないか
- **実在:** 設計が使う既存の型、関数、ファイルが、本当にその形で存在するか
- **型と境目:** 型と関数の形がはっきりしているか。入力の検証とエラーの扱いが覆われているか。`any` のような
  危うい書き方を前提にしていないか
- **見通し:** 責務が分かれているか。テストしやすいか。要件に対して複雑すぎないか
- **実装計画:** 途中で `pnpm check` が通らない順になっていないか

## 報告

- **判定:** 重大な問題があれば `issues`、なければ `ok`
- **問題:** 問題ごとに、題、内容、影響、直し方の案、関係する受け入れ基準の番号、設計の文書の場所（節）。
  `ok` なら「なし」
- **良いところ:** 1〜2 個。判定が `issues` でも書く
